# Sophie — Architecture

## Layering

```
UI (Streamlit)
    -> Application / Services   (sophie.services)
        -> Domain                (sophie.domain)
        -> Repositories           (sophie.repositories)
        -> Providers              (sophie.providers.*)
```

- **`sophie.domain`** — pure Python/Pydantic types and pure functions: training rules, load
  scoring, recovery deviation, aerobic efficiency, etc. No I/O, no framework imports. This is the
  most heavily tested layer.
- **`sophie.services`** — orchestration: import pipelines, planner, Sunday Review workflow, coach
  orchestration (deterministic + LLM), memory, decision log. Depends on domain + repositories +
  providers. No Streamlit import.
- **`sophie.repositories`** — SQLAlchemy-backed persistence, one repository per aggregate root
  (workouts, summaries, plans, lab results, ...). Only place that talks SQL/ORM.
- **`sophie.providers.*`** — external system adapters: `apple_health` (XML/ZIP parsing),
  `sports_tracker` (FIT/GPX), `calendar` (Microsoft Graph via MSAL + an ICS/mock fallback),
  `weather` (Open-Meteo-style HTTP provider behind an abstract interface), `llm` (OpenAI + a
  deterministic-only fallback), `clinical` (CSV/JSON/PDF lab import).
- **`sophie.ui.streamlit`** — presentation only. Calls services, renders results, collects input.
  Nothing here is unit-tested for business correctness; it is smoke/manually tested.

**Rule:** `grep -rl streamlit src/sophie` must only ever match files under `src/sophie/ui/streamlit/`.
This is checked by `tests/unit/test_architecture_boundaries.py`.

## Why this shape

Streamlit is explicitly a *current* presentation layer (see build brief §7). A future Next.js /
FastAPI / mobile frontend must be able to reuse `services` + `domain` + `repositories` +
`providers` unchanged. Putting business logic in Streamlit callbacks would block that.

## Database portability

- SQLite now, via SQLAlchemy 2.x Core/ORM — the same models can point at Postgres later by
  swapping the engine URL; no SQLite-specific SQL is used in models.
- Alembic migrations from schema version 1 (`src/sophie/db/migrations`).
- Every user-owned table carries a `profile_id` (UUID) foreign key, even though the product is
  single-user today — this avoids a future multi-user migration rewrite. No authentication is
  implemented; there is exactly one local `Profile` row created on first run.
- Stable UUIDs (`uuid4`, stored as `CHAR(36)`) are primary keys for user-owned aggregate roots
  (workouts, plans, sessions, lab results, ...); small lookup/reference tables may use surrogate
  integer keys.
- SQLite foreign keys are enabled via a `PRAGMA foreign_keys=ON` connect event.
- Multi-step state changes (e.g. plan approval + calendar write-back + decision log entry) run
  inside a single SQLAlchemy transaction/session with explicit commit/rollback.

## Import & data pipeline

```
raw file (ZIP/XML/FIT/GPX/CSV/JSON/PDF)
    -> provider parser (streaming where large)          [sophie.providers.*]
    -> import_manifest row (fingerprint, idempotence)    [sophie.repositories.import_manifest]
    -> canonicalization / normalization                  [sophie.services.import_pipeline]
    -> canonical_workout / daily_health_summary / lab_result / body_composition_assessment
    -> weekly_summary / training_load / recovery / ... derived tables (batch recompute)
```

Raw source files (ZIP, XML, FIT, GPX, clinical PDFs) are never persisted by Sophie — they are read
from wherever the user points Sophie, processed into normalized rows, and (for temp
extraction, e.g. an Apple Health ZIP) deleted afterward. See `docs/PRIVACY.md`.

## Coach architecture

`sophie.services.coach` orchestrates:

1. Build a `CoachContext` (sanitized summaries, config, block, domain statuses, memory) —
   no raw health/calendar data.
2. If an LLM provider is configured and reachable, ask it for a structured `CoachRecommendation`
   (JSON schema enforced client-side via Pydantic).
3. Run `sophie.domain.coach_validation.validate_and_repair(...)` — deterministic rules (session
   count, block conformance, long-run range, quality limits, padel/load spacing, calendar
   feasibility, recovery/pain gating). Repair safely where possible; otherwise one structured
   regeneration attempt against the LLM; otherwise fall back to a fully deterministic plan
   generated by `sophie.domain.planner`.
4. The validated recommendation (never raw LLM output) is what the UI shows for approval.

If no LLM key is configured, or the call fails, Sophie skips straight to the deterministic
planner — the product must remain fully usable with zero LLM access.

## Calendar feasibility engine

`sophie.services.calendar_feasibility` is independent of the coach: it takes busy/free intervals
(from the Outlook provider or a mock/ICS fallback), the target week, session durations/buffers,
padel, training load/recovery status, weather, and user scheduling preferences, and returns ranked
candidate windows with rejection reason codes for infeasible ones. The LLM never invents calendar
availability — it only picks among windows this engine already produced.

## Cross-cutting

- Centralized timezone handling: `sophie.config.timezone` (defaults from `SOPHIE_TIMEZONE`, all
  stored timestamps are UTC, converted at the edges).
- Centralized units: `sophie.domain.units` (metric internally; display formatting is a UI concern).
- Centralized configuration: `sophie.config.settings` (`pydantic-settings`, reads `.env`).
- Derived calculations carry `source`, `calculation_version`, and `data_quality` so any health
  domain status can answer "where did this come from?" (see `docs/DATA_DICTIONARY.md` §Provenance).
